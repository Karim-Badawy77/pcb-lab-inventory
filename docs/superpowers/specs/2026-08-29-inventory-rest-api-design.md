# PCB Lab Inventory REST API Design

## Purpose

Build a backend REST API for a future Vue.js inventory frontend. The API will use Node.js, Express, CommonJS modules, MongoDB, and Mongoose. MongoDB database `pcb-inventory` will contain the `items` and `history` collections.

This first version is an unauthenticated internal API. Each item represents one physical inventory object; quantity tracking is out of scope.

## Architecture

Use a layered Express architecture following MVC boundaries:

- `routes/` maps HTTP methods and paths and applies upload middleware.
- `controllers/` translates HTTP requests into service calls and formats responses.
- `services/` owns inventory rules, item state transitions, soft deletion, and automatic history creation.
- `models/` defines the Mongoose schemas for items and history.
- `middleware/` provides validation, upload handling, not-found handling, and centralized error responses.
- `config/` loads configuration and connects to MongoDB.
- `uploads/` stores item images and is exposed through an Express static route.
- `tests/` covers services and HTTP endpoints.

Controllers will remain thin. Services will update an item and create its transaction history in one MongoDB session and transaction. Production MongoDB must therefore support transactions. Tests will use an in-memory replica set.

## Item Model

The `items` collection contains:

- `_id`: MongoDB ObjectId.
- `images`: optional array of image records. Each record contains its own `_id`, `path`, `originalName`, and `uploadedAt`.
- `dates.created`: creation timestamp.
- `dates.modified`: most recent modification timestamp.
- `stored`: Boolean inventory-state flag.
- `deleted`: Boolean soft-deletion flag, defaulting to `false`.
- `location`: object containing string fields `warehouse`, `section`, and `pack`.
- `owner`: string.
- `category`: string.
- `description`: string.
- `tags`: array of editable strings.
- `updates`: editable array of records containing `_id`, `text`, and `createdAt`.
- `name`: string.
- `part_num`: string.
- `delivered_by`: string.
- `delivered_to`: string.

Mongoose timestamps or equivalent model middleware will maintain the two values under `dates`.

### Item State Invariants

A stored item must have `stored: true`, a valid `location`, and no `delivered_to` value.

A delivered item must have `stored: false`, no active location values, and a nonempty `delivered_to` string.

Transitioning an item to delivered automatically clears its location. Transitioning it back to storage automatically clears `delivered_to` and requires a location.

A deleted item remains in the collection with `deleted: true`. Deletion is not reversible in this version.

## History Model

The `history` collection records inventory transactions, not ordinary metadata edits. Each document contains:

- `_id`: MongoDB ObjectId.
- `item_id`: ObjectId reference to the related item.
- `date`: transaction timestamp.
- `from`: the prior storage location, delivery destination, or `null` for a new item.
- `to`: the new storage location, delivery destination, or the exact string `"deleted"` for soft deletion.
- `delivered_to`: string when relevant to the transaction.
- `new_item`: Boolean that is `true` only for the initial item transaction.

The `from` and `to` fields must support location objects and state-marker strings. History records are generated by item operations and are not directly editable through public endpoints.

History is created when:

- An item is created.
- Its location changes.
- It moves between stored and delivered states.
- Its delivery destination changes as part of an inventory transaction.
- It is soft-deleted.

Edits to names, descriptions, categories, tags, item updates, ownership, part numbers, or images do not create history records.

## REST API

All inventory and history behavior is coordinated through the item resource. There are no standalone history mutation endpoints.

### `POST /api/items`

Create an item. Accept `multipart/form-data`, with item data plus zero or more files in the `images` field. Create the item and an initial history record with `new_item: true` atomically.

### `GET /api/items`

Return paginated, non-deleted items by default. `includeDeleted=true` includes soft-deleted items. Pagination parameters will be documented and given safe defaults.

### `GET /api/items/:id`

Return one item together with its transaction history. A soft-deleted item is hidden by default and can be retrieved only when the deleted-item query option is explicitly enabled.

### `PATCH /api/items/:id`

Partially update metadata, tags, item updates, images, or inventory state. Accept `multipart/form-data` when adding images. Existing images can be retained, new images appended, and individual images removed by image `_id`.

The service compares the prior and requested inventory state. It creates history only if the request represents an inventory transaction.

### `DELETE /api/items/:id`

Soft-delete an active item by setting `deleted: true`. Atomically add a final history record with `to: "deleted"`. Deleting an already deleted item returns `409 Conflict` and does not add duplicate history.

## Image Lifecycle

Multer or equivalent Express middleware will accept multiple image files under the `images` field. Files will be stored beneath `uploads/`, and Express will expose a public URL prefix for them.

Upload configuration will restrict allowed image MIME types, maximum file size, and maximum image count. These limits will come from environment configuration with documented defaults.

Add to name of images timestamp when saving in `uploads/` to avoid replica.

If request validation or database work fails, newly uploaded files must be removed. When an existing image is removed from an item, its local file will be deleted only after the corresponding database operation succeeds. This sequencing prevents database references to missing files during a failed transaction.

## Validation and Errors

Validate request structure, MongoDB IDs, required item state fields, state invariants, upload count, file size, and file type.

Use a consistent JSON response envelope:

```json
{
  "success": true,
  "data": {}
}
```

Errors use the same stable shape with `success: false` and a useful message. Expected status codes include:

- `400 Bad Request` for malformed or invalid input.
- `404 Not Found` for missing or normally hidden items.
- `409 Conflict` for contradictory state transitions or repeated deletion.
- `413 Payload Too Large` for uploads beyond configured limits.
- `500 Internal Server Error` for unexpected failures.

Centralized middleware will prevent internal stack traces and implementation details from leaking in production responses.

## Configuration

Use environment variables for at least:

- `PORT`
- `MONGODB_URI` (pointing to database `pcb-inventory`)
- maximum image count
- maximum image size
- allowed image MIME types

Provide `.env.example` without credentials and a README covering installation, configuration, development, testing, and endpoint usage.

## Testing

Use Jest, Supertest, and an in-memory MongoDB replica set. Tests will cover:

- Item and history schema validation.
- Creation and automatic initial history.
- Item listing, lookup, partial updates, and soft deletion.
- Stored-to-delivered and delivered-to-stored transitions.
- Location and delivery transaction history.
- The absence of history for metadata-only changes.
- Editable tags and item updates.
- Multiple-image upload, retention, and individual removal.
- Cleanup of uploaded files when a request fails.
- Atomic rollback when either item or history persistence fails.
- Deleted-item filtering and repeated-deletion conflicts.
- Consistent validation and error response formats.

## Out of Scope

- Authentication and authorization.
- Vue.js frontend implementation.
- Quantity or aggregate stock tracking.
- Cloud image storage.
- Direct history creation, editing, or deletion endpoints.
- Restoring soft-deleted items.
